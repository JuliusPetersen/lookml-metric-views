LookML to metric views
Try it Source on GitHub

Product notes

Julius Petersen, November 2026. Independent work from public sources, not reviewed by Databricks.

The problem

Databricks tested Genie One on 125 business questions in November 2026. With tables only it answered 64% correctly. With governed definitions in Unity Catalog metric views and curated agents it reached 93 to 95%.1 Getting a company's definitions into metric views is therefore the step that decides whether its users can trust Genie.

Databricks has built that step for two BI tools. Genie Code's /importBI reads Tableau and Power BI files and creates metric views, now in bulk.2 Genie Ontology reads Power BI models today, with Tableau and Sigma announced.3 Looker is not on either list as of 25 November 2026. A Looker team on Databricks has its definitions in LookML and two options: rebuild them by hand, or let Genie work on raw tables.

Who it is for

  • An analytics engineer at a company that runs Looker on Databricks and wants AI/BI dashboards or Genie on the same numbers.
  • A Databricks solutions architect or partner who scopes a Looker migration and needs to know in an hour how much of a project translates without work.

What it does

It reads a LookML project and writes one metric view per explore, with the explore's joins, its dimensions as fields and its measures as measures. Every item gets one of four statuses with a reason: exact, adapted, review or manual. It also writes the SQL to create the views and queries to reconcile totals against Looker before anything is switched off.

Decisions

DecisionWhy
One metric view per explore, not per viewPeople query explores, and an explore is where Looker defines joins. Converters that work per view lose the joins. That includes the Apache Ossie path, whose Databricks deploy writes one metric view per dataset without joins.
Rules, not a language modelThe same project gives the same output every time, so it can run in CI and be reviewed like code. A model can still help with the items marked manual, with the report as its task list.
Flag instead of guessA migration that is 95% right and silently wrong in the rest is worse than one that says where the 5% is. Anything that can change a number is marked review, with the reason.
Runs in the browserTeams can try it on a private project without uploading their LookML anywhere.
SQL translation only for the LookML snippetsLooker on Databricks already writes Spark SQL, so most of the work is structure. For BigQuery or Snowflake projects, each snippet is translated with sqlglot before references are filled in.

What testing changed

I created the generated metric views in a Databricks Free Edition workspace and compared every measure with SQL that reproduces Looker's results. Two findings changed the tool.

Sums over joined views. In Looker, a sum over a joined view counts each joined row once (symmetric aggregates). In a metric view the same expression counts once per row of the base table. On TPC-H, the order value measure in the order lines explore came out at 4.9 times Looker's value. The first version marked it exact. It is now marked review with that explanation, and the live check confirms that every other measure matches.

Subqueries. The first version flagged every subquery as risky. The live test showed that Databricks accepts subqueries that refer to a joined table, but rejects correlated subqueries that refer to the base table. The tool now marks exactly that case as manual. After the change, all five metric views from Looker's public thelook project were created without edits.

Evidence

  • Live check in Databricks: 16 measures, 15 exact matches, 1 expected difference.
  • Survey of 42 public Looker projects: 81% of 29,248 fields, measures and joins translate without a person, 72% in the median project. One project holds 36% of the items, and without it 71% translate. 8 of 42 projects gave no metric view.
  • 25 automated tests on the hard cases: nested joins, fan-out, filters, Liquid, one-to-many and many-to-many joins, derived tables, LookML constants, extends and refinements.

What exists already

I searched Databricks' docs and release notes, GitHub, package indexes, standards bodies and community forums on 25 November 2026 (16 query groups). Closest matches:

  • /importBI and Genie Ontology: Tableau and Power BI, not Looker.
  • Apache Ossie converters: Ossie to Databricks metric views exists, LookML import is on the roadmap. The Databricks deploy keeps relationships out of the metric views.
  • Sidemantic (AGPL): reads LookML into its own runtime; Liquid, includes and sets are not supported.
  • lkml2cube, dbt-converter, Honeydew: LookML into Cube, dbt and Honeydew, not Databricks.
  • A step-by-step guide for a manual LookML to metric view migration (typedef.ai, December 2025).

I found no tool that turns a LookML project into Databricks metric views per explore with a field-level report. That is a statement about this search, not proof that none exists.

Not validated yet

  • I don't know how many Databricks customers run Looker, so the size of the problem is open.
  • The reference numbers come from SQL I wrote to reproduce Looker's logic, not from a Looker instance.
  • No conversations with analytics engineers who run Looker on Databricks yet, so the user problem is supported by public evidence, not by interviews.
  • Not translated: Liquid templating, Looker parameters, access filters, extends and refinements of explores, sets in field lists, fiscal timeframes and display formats.
  • Timezone conversion depends on Looker connection settings, which a LookML project doesn't contain.

What the survey changed

The first survey run crashed on one explore in 11 of the 42 projects. Most used LookML constants like @{schema} from the project's manifest, which the tool now fills in and reports. It also showed that Liquid templating is the largest blocker: 46% of the items that need a person use it. That decides what a Databricks version would have to solve first.

If Databricks built this into /importBI

Accept a LookML repository as a source next to Tableau and Power BI files. The primary metric would be the share of LookML measures that reach Unity Catalog without edits, with the reconcile step built in. The guardrail is the share of migrated measures whose totals differ from Looker without a warning, which has to stay at zero. A pilot with five Looker customers would count as a success if at least 70% of their measures reach Unity Catalog without edits and the guardrail holds. 70% is my assumption, close to the survey's median project. Next steps in order of value: resolve the most common Liquid patterns, templated filters ({% condition %} in 20 of the 42 projects, date_start and date_end in 17) and parameters (23), map Looker parameters to metric view parameters, read real results through the Looker API for automatic reconciliation, and turn access filters into Unity Catalog row filters.
